# ADR-0005: Application Service をトランスポート非依存に保つ

- ステータス: 承認済み
- 判断日: 2026-04-01
- 記録日: 2026-08-23
- 関連: [Issue #3](https://github.com/Ries630/BlazorCleanShop/issues/3)、[当初の設計会話](https://claude.ai/share/081f3e76-b272-49f4-9f1c-de15f8b0b5d4)

## 背景

将来、他システムとの API 連携、マイクロバッチ、ファイル連携を追加する構想がある。
Blazor UI、HTTP API、バッチのどの入口からも同じビジネスロジックを利用できることが
望まれている。

現時点では、Batch や ExternalApi のプロジェクトを必要とする具体的な機能はない。
先に空のプロジェクトを作るのではなく、Application 層を特定の入出力方式から独立させて
おけば、必要になった時点で新しい入口を追加できると判断した。

## 決定

Application Service の引数と戻り値には DTO、Command、値を使用し、`HttpRequest` や
`IResult` など特定のトランスポートの型へ依存させない。

ファイル出力や外部 API クライアントなど、ユースケースが必要とする外部 I/O の
インターフェースは Application 層に置き、実装は Infrastructure 層に置く。Batch や
ExternalApi などの新しい入口は、具体的な機能が必要になった時点で別プロジェクトとして追加する。

## 検討した代替

### Application Service で HTTP の型を直接扱う

Minimal API からは値をそのまま受け渡しやすくなる。しかし、バッチやファイル連携から
同じ Service を呼ぶときにも HTTP への依存が必要になるため採用しない。

### Batch と ExternalApi のプロジェクトを先に作る

将来の構成を最初から見える形にできる。しかし、まだ実装する機能がなく、空のプロジェクトと
設定だけが増えるため採用しない。

## 結果

- Minimal API や Blazor Component は、トランスポート固有の入力と Application 層の
  DTO、Command、戻り値を変換する必要がある
- Application Service から `IResult` や HTTP ステータスを直接返せない
- HTTP ステータス、画面遷移、ファイル形式などの表現は各入力アダプター側で決める必要がある
- 新しい入口を既存ホストへ安易に同居させず、別プロジェクトの起動構成と DI 登録を
  用意する必要がある
- バッチ固有の処理が既存ユースケースと異なる場合は、新しい Application Service の設計が必要になる

## 再評価のサイン

- 今後も入口が一種類だけであり、トランスポート非依存の境界が継続的な負担になった
- 外部連携またはバッチの具体的な要件が決まり、新しいプロジェクトを作成する時点になった
- トランスポート固有の制約がユースケースの成立条件そのものになった
- 外部 I/O の抽象と Domain 層のビジネスルールを分離できない事例が増えた
