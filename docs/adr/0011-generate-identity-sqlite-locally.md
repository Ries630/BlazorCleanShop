# ADR-0011: Identity 用 SQLite DB をマイグレーションからローカル生成する

- ステータス: 承認済み
- 日付: 2026-08-25
- 関連: [Issue #20](https://github.com/Ries630/BlazorCleanShop/issues/20)

## 背景

`src/BlazorCleanShop.Web/Data/app.db` と Identity のマイグレーションファイルが Git で
追跡されていた。DB の `__EFMigrationsHistory` は
`20250709153422_CreateIdentitySchema`（EF Core 10.0.0-preview.7）を適用済みとしているが、
追跡中のマイグレーション ID は `00000000000000_CreateIdentitySchema`（EF Core 10.0.0）で
一致していなかった。

EF Core 10.0.11 では追跡中のマイグレーションが未適用と判定され、既存 DB に
`dotnet ef database update` を実行すると `AspNetRoles` の重複作成で失敗した。一方、
DB を置かずに同じマイグレーションを適用すると新しい DB を生成でき、モデルにも
未反映の変更はなかった。生成後は Web のトップと Identity の登録画面がどちらも
HTTP 200 を返した。

判断時点で追跡 DB の `AspNetUsers` は 0 件だった。DB は WAL モードであり、開くと
`app.db-wal` と `app.db-shm` が未追跡ファイルとして生成された。

## 決定

Identity 用 SQLite DB と WAL の副ファイルは Git で追跡せず、ローカル環境ごとに
EF Core マイグレーションから生成する。マイグレーションファイルと、EF Core と同じ
バージョンの `dotnet-ef` ローカルツール定義を Git で追跡する。

DB の生成は開発者が `dotnet ef database update` を明示的に実行する。アプリケーション
起動時の自動マイグレーションは行わない。

## 検討した代替

### 追跡 DB を修復して維持する

DB の履歴 ID を修正すれば現在の不整合は解消できる。しかし、以後もスキーマ変更ごとに
マイグレーションとバイナリ DB の両方を更新する必要があり、差分をレビューできない。
開発者が作成したアカウントや WAL の副ファイルが混入する余地も残るため採用しない。

### アプリケーション起動時に自動適用する

初回起動だけで DB を生成できる。しかし、起動処理がスキーマ変更を伴い、開発者が
マイグレーション適用を明示的に確認できなくなる。現時点ではローカル開発用 DB だけが
対象であり、別の自動適用経路を追加する必要がないため採用しない。

## 結果

- 新規 clone 後はツール復元とマイグレーション適用を行うまで Identity DB が存在しない
- ローカルで作成したアカウントは他の開発環境へ共有されない
- ローカル DB を削除するとアカウントデータは失われ、マイグレーションで復旧できるのは
  スキーマだけである。必要なローカルデータは削除前に DB を退避する必要がある
- 判断時点の追跡 DB はユーザー 0 件だったため、今回移行するアカウントデータはない
- `dotnet-ef` のバージョンを EF Core のパッケージ更新と合わせて管理する必要がある

## 再評価のサイン

- 事前投入済みのデモデータをリポジトリと一緒に配布する要件が生じた
- 本番環境向けのDB移行方式を決める段階になった
- 開発環境の初期化を自動化する専用ホストやセットアップ処理が必要になった
