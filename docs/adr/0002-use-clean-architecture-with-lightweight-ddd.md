# ADR-0002: クリーンアーキテクチャと軽量 DDD を採用する

- ステータス: 承認済み
- 日付: 2026-03-30
- 関連: [Issue #3](https://github.com/Ries630/BlazorCleanShop/issues/3)、[当初の設計会話](https://claude.ai/share/081f3e76-b272-49f4-9f1c-de15f8b0b5d4)

## 背景

このプロジェクトは、デモショッピングサイトの実装を通じてデザインパターンを学ぶことを
主目的の一つとしている。ただし、学習のために実務上不要な複雑さを持ち込まず、
小規模なアプリケーションで扱いやすい範囲に留める方針も示されていた。

当初の会話では、Entity を DTO と同じデータ入れ物として扱う従来の実装経験に対し、
ビジネスルールを持つ Entity、値で等価性を判断する Value Object、Domain 層に置く
Repository インターフェースを区別して学ぶことが確認された。

また、レイヤーを一つのプロジェクト内のフォルダーだけで分ける方法と、レイヤーごとに
独立した `.csproj` を設ける方法を比較した。フォルダー分けだけでは依存方向が開発者の
自制に依存する一方、プロジェクトを分ければ不正な参照をコンパイルエラーにできる。

## 決定

Domain、Application、Infrastructure、入力アダプターを分離するクリーン
アーキテクチャを採用し、レイヤーごとに独立した `.csproj` を設ける。Domain 層には
ビジネスルールを持つ Entity、Value Object、Repository インターフェースを置く。

DDD はこの範囲に限定して軽量に採用する。CQRS、MediatR、Domain Events、
Specification パターンは現時点では採用しない。

## 検討した代替

### 一つのプロジェクト内でフォルダーだけを分ける

プロジェクト数と参照設定を減らせる。しかし、Domain 層から Infrastructure 層を
参照しないという規則をコンパイラで強制できないため採用しない。

### Entity をデータ入れ物とし、Service にロジックを集約する

既存の実務経験に近い構成にできる。しかし、Entity と DTO の役割を分け、Entity 自身に
生成規則や状態変更のルールを持たせることが今回の学習対象であるため採用しない。

### CQRS、MediatR、Domain Events、Specification パターンまで導入する

より複雑なユースケースを分割・連携する選択肢になる。しかし、小規模なデモアプリでは
学習コストに対する効果が薄いと判断したため、最初からは導入しない。

## 結果

- 一つのプロジェクトで完結する構成より、プロジェクト数と参照設定が増える
- レイヤーをまたぐデータには DTO や明示的な変換が必要になる
- Domain 層から外側の実装を直接利用できず、必要な機能はインターフェースを介して
  依存方向を保つ必要がある
- CQRS による読み書きモデルの分離、Domain Events による処理の分離、Specification
  による検索条件の部品化は利用できない
- 採用しなかったパターンが必要になった場合、既存のユースケースや依存関係を
  段階的に組み替える必要がある

## 再評価のサイン

- 読み取りと更新で必要なモデルや最適化方法が明確に分かれた
- 一つのドメイン変更を複数の独立した処理へ通知する必要が生じた
- Repository の検索条件を複数のユースケースで組み合わせる重複が増えた
- 現在のプロジェクト境界が、依存方向の保護より開発上の障害を多く生むようになった
